# Ранбук выката профилей скоринга (ADR 0002, сессия G)

Как выполнять:

- **SQL** — файлы этой папки из своей копии репозитория, на РФ-ядро:

  ```sh
  ssh <РФ-ядро> 'docker exec -i oiltech_pg psql -U oiltech -d oiltech_digest -X -v ON_ERROR_STOP=1' \
    < scripts/g/<файл>.sql
  ```

- **CLI на ядре:** `ssh <РФ-ядро> 'docker exec oiltech_app python -m oiltech_digest.cli …'`.
- **Проверка после каждого шага** — `scoring-profiles-check.sql`, только чтение.

Каждый SQL-файл повторяется без ошибок, кроме копии баллов: её повтор откажет, и это нарочно. Все
файлы проверены тестами на данных как на проде (`tests/test_scoring_rollout.py`).

## Выкат

1. **Схема до выката** — `scoring-profiles-before-deploy.sql`.
   - Окно: без ИИ-аренд, `cli live-ai-leases` пуст.
   - Отказ по `lock_timeout` ничего не меняет — повторить позже.
   - Проверка: у всех критериев профиль `business`, сумма активных 100.
2. **Ядро:** `sh scripts/deploy-core.sh --no-schema app scheduler worker playwright-worker`.
3. **Индекс и профиль радара** — `scoring-profiles-after-deploy.sql`, затем `cli seed-scoring`.
   - Ожидаемый вывод: «tech_radar: заведено 5, сумма весов=100», «business: не тронут».
   - Если сид отказал с `idx_scoring_criteria_name`, значит, файл шага 3 не выполнен. Сид при этом
     ничего не записал.
4. **NL:** `sh scripts/deploy-nl.sh`.
   - Не в первый цикл планировщика после 00:00 МСК: в `cli external-queues-status` у
     `external-agents` должно быть running=0.
5. **Набор заказчика в профиле business**
   1. Попросить заказчика закрыть экран «Скоринг» до конца шага. Вкладка, открытая до смены
      набора, сохранить уже не сможет: она получит «список устарел — обновите страницу», а
      набранные в ней правки пропадут.
   2. Сухой прогон: `cli apply-scoring-preset --profile business --preset viktor`.
      - Вывод: «до» и «после» с суммами, строка «id прежнего набора» с готовым откатом.
      - **Записать эту строку.** На проде 29.09 id были 789, 3, 791, 792, 793. Если в выводе
        другие — брать из вывода.
   3. Запись: то же с `--apply`.
   4. Сверка по `scoring-profiles-check.sql`, запрос 2.
      - В `business` ровно пять критериев: «Стратегическая значимость для нефтесервиса» 30,
        «Потенциальный бизнес-эффект» 25, «Рыночная возможность / изменение рынка» 20,
        «Практическая применимость» 15, «Достоверность и актуальность» 10.
      - В `tech_radar` — прежние пять.
      - С этого момента новые статьи считаются набором заказчика, старые — прежним до пересчёта.
6. **Пересчёт сентября с ИИ — не позже 04.10 МСК и ровно один раз.** С 05.10 сентябрь в архиве, и
   `enqueue-rescore` откажет.
   1. **Полоса пересчётов.** Без неё около 143 задач встали бы в поток дня `external-ai` перед
      новыми статьями: 18.09 28 пачек задержали его на 4,5 ч.
      - Ядро: `ssh <РФ-ядро> 'docker exec oiltech_app printenv AI_BULK_LANE_ENABLED'` — должно
        быть `1`.
      - NL: `ssh <NL> "docker ps --filter name=oiltech_external_worker_bulk --format '{{.Names}} {{.Status}}'"`
        — должно быть `Up …`.
      - Если выключено: сначала поднять `external-worker-bulk` на NL, затем прописать
        `AI_BULK_LANE_ENABLED=1` в `.env` РФ и пересоздать app — `sh scripts/deploy-core.sh app`.
   2. Сухой прогон: `cli enqueue-rescore --profile business --month 2026-09`. Показать владельцу N
      и стоимость. В выводе должны быть:
      - N и сколько из них в выпусках;
      - стоимость;
      - строка «полоса: external-ai-bulk (external); воркеры полосы: nl-ai-bulk-1 (задачу просил …)»;
      - ни одной строки «ВНИМАНИЕ».
   3. **Копия баллов сентября** — `scoring-backup-2026-09.sql`. Файл печатает число баллов и
      подпунктов в копии. Пересчёт удаляет прежние подпункты, без копии их не вернуть.
   4. С «да» владельца, один раз: `cli enqueue-rescore --profile business --month 2026-09 --no-dry-run`.
      - Без полосы пересчётов команда откажет.
      - Повторный запуск статьи из ещё не исполненных задач не ставит, но он и не нужен.
   5. Ход: в `cli external-queues-status` очередь `external-ai-bulk` убывает. После пересчёта:
      - `scoring-profiles-check.sql`, запрос 4: у новых баллов профиль `business` и снимок;
      - повторный сухой прогон даёт N около 0.
   6. После приёмки удалить копию:
      `DROP TABLE g_backup_article_score_items_2026_09, g_backup_article_scores_2026_09;`

## Откаты

- **а. Код на прежнюю сборку после шага 3.**
  1. Если пресет уже применён и нужен прежний набор — сначала откат «б».
  2. `scoring-profiles-rollback.sql`: `DELETE FROM scoring_criteria WHERE profile = 'tech_radar'`,
     затем `CREATE UNIQUE INDEX idx_scoring_criteria_name ON scoring_criteria(name)`.
  3. **Только потом** выкат старого кода. Старый код читает критерии без фильтра профиля: с
     профилем радара он увидел бы сумму 200, баллы через NL молча раздулись бы. Его «Сохранить»
     без глобального индекса имён падает.

  Колонки профиля остаются, старому коду они не мешают. До шага 3 откат кода — просто выкат
  старого кода.
- **б. Набор business — к прежнему.** Выполнить UPDATE из вывода сухого прогона шага 5. На проде
  29.09:

  ```sql
  UPDATE scoring_criteria SET enabled = id IN (789, 3, 791, 792, 793), updated_at = now()
  WHERE profile = 'business';
  ```

  Набор заказчика выключится, прежний включится: веса выключенных пресет не менял. Сверка — запросы
  1–2 `scoring-profiles-check.sql`, сумма 100. Баллы, пересчитанные набором заказчика, это не
  возвращает — для них откат «в».
- **в. Пересчёт — к прежним баллам.**
  1. `scoring-rescore-cancel.sql` снимает ещё не выданные задачи пересчёта.
  2. Дождаться running=0 у `external-ai-bulk` (`cli external-queues-status`).
  3. `scoring-restore-2026-09.sql` возвращает итог, профиль, снимок и подпункты из копии. Баллы,
     которых в копии нет, не трогаются.

## P0 — два предусловия, вскрытых разведкой. Проверены руками, не со слов агента

### 1. `python-multipart` не установлен — контейнер `app` не поднимется

FastAPI роняет **определение маршрута**, а не запрос. Проверка:

```
.venv/bin/python -c "from fastapi import FastAPI, File, UploadFile; app=FastAPI(); @app.post('/x')..."
→ RuntimeError: Form data requires "python-multipart" to be installed
```

То есть первый же `UploadFile` в `api.py` роняет импорт модуля, bootstrap падает, `app`
не встаёт по `condition: service_completed_successfully`. Это не «мелочь в спеку» —
это строка в `requirements.txt`, без которой фича не деплоится вообще.

### 2. Тесты фронта на `origin/main` уже КРАСНЫЕ

```
Test Files  1 failed | 1 passed (2)
      Tests  1 failed | 13 passed (14)
```

`App.test.tsx:672` — тест ручного импорта статьи ходит на `?screen=sources`, но
`URL_ADDRESSABLE` (`App.tsx:165`) содержит только `["jobs","maintenance","tech-preview","analytics-preview"]`.
Тест уехал в `origin/main` красным вместе с коммитами ручного импорта 04–06.08, и никто
не заметил, потому что **CI в репозитории нет** (`.github` отсутствует), а Docker собирает
фронт `vite build` без `tsc` (`Dockerfile:13`, тех-долг T12).

Определение готовности (DoD) в `SPRINT_PLAN.md` требует зелёных тестов. Значит либо чиним
до начала фичи (одна строка в массиве), либо явно фиксируем как унаследованный красный
и не считаем его своим.

**Python-набор при этом зелёный: `251 passed` на `feat/upload-docs`.** Из них 39 требуют
живого Postgres и без него падают ОШИБКОЙ, а не скипаются — контейнер `oiltech_pg` должен быть поднят.

## Ш2. Тикеты — `/to-tickets`

**Тоже в том же окне, сразу после спеки.**

```
/to-tickets Разбей спеку #<НОМЕР_СПЕКИ> на тикеты-трассеры.

Учти при нарезке:
```

## Параллельные дорожки — можно запускать прямо сейчас, они не ждут спеки

### П1. Спайк PDF-парсера — блокирует Р2/Р11 в спеке

Нужны **3 реальных документа** того типа, что реально ходят по рукам (Родионов обещал
запросить примеры у ГД на встрече 09.07). Без них выбор парсера — гадание.

Отдельная сессия:

```
Спайк: выбрать PDF-парсер под фичу «приём файлов». Разведи воркфлоу — кандидаты независимы, меряются одинаково.

Требование к результату: текст с НАДЁЖНОЙ привязкой к номеру страницы. От этого зависят Р2 (факт со ссылкой на страницу) и Р11 (машинная сверка числа с текстом той страницы). Парсер, который отдаёт плоскую простыню, фичу не поддерживает.

Кандидаты: pypdf, pdfplumber, PyMuPDF.
Документы: <пути к трём файлам>

По каждому кандидату на КАЖДОМ документе замерить:
- полноту извлечения (знаков) и видимые потери: таблицы, многоколоночная вёрстка, колонтитулы
- корректность привязки к странице: взять 10 чисел, про которые известно, на какой они странице, и проверить, что парсер кладёт их на ту же
- пиковую память процесса и время. На проде 1.9 ГБ RAM и задокументированный OOM — это отборочный критерий, не косметика
- лицензию ПО ПЕРВОИСТОЧНИКУ (PyPI + репозиторий проекта), а не по памяти модели. У PyMuPDF предположительно AGPL-3.0 — если так, для поставки по договору ГПХ в ГПН это блокер, и надо это подтвердить или опровергнуть ссылкой

Отдельно: как определять скан (документ без текстового слоя) и что предлагается делать. В v1 решено отклонять с честным сообщением, проверь, что предложенный критерий отличает скан от документа с редким текстом.

Ничего не ставить в проект: временный venv в скретчпаде, requirements.txt не трогать.
Вывод: таблица сравнения + рекомендация + чем она доказана.
```

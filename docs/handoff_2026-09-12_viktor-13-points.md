## 🚦 Три вещи, которые меняют постановку

### 1. Пункт 9 по коду не воспроизводится

«Одна новость может быть в разных тегах» — **технически невозможно**. На `article_tags`
висит `CREATE UNIQUE INDEX idx_article_tags_article_unique ON article_tags(article_id)`
(`schema.sql:191`) — уникальность по **article_id**, а не по паре. Вторая строка для той же
статьи физически не вставится. Плюс схема ответа модели принимает **скалярный** `tag_id`,
а не список (`prompts.py:149-161`), и лента кладёт статью ровно в одну группу
(`ArticlesPage.tsx:263-269`).

Единственный механизм, при котором «одна новость в разных тегах» **реально наблюдается** —
**перепечатки**: при вставке отсекается только точное совпадение URL
(`repository.py:2631-2646`, `ON CONFLICT (url) DO NOTHING`), каждая копия тегируется
независимым вызовом модели, согласованность тегов между копиями не гарантирует ничто.

**Вывод: пункт 9 — это не теги, это дедуп (#60, №21).** Он уезжает не в агентную задачу, а
в «удаление технических дублей» — состав **этапа 1** по договору. Нужен один скриншот от
Виктора, чтобы закрыть развилку: два разных `article_id` или одна строка показана дважды.

### 2. Пункты 3, 9 и 10 похожи на заказ по макету, который мы сами ему показали

`frontend/src/features/previews/TechnologiesPreview.tsx` — **статический прототип** (файл
сам это объявляет в шапке, строки 5-9), подключён в `App.tsx:328`. На его карточках:

- `tags: string[]` + `extraTags: number` — **несколько тегов на карточку** (строки 130-131);
- `rating: number; ratingsCount: number` — **оценка 1–5 со счётчиком оценивших**,
  на экране «4.6 (12 оценок)» (строки 137-138, 459, 516-517).

Живых данных за этим экраном нет ни одного. Если Виктор видел его, то пункт 3 — это не
«поле для админа», а **оценка от многих пользователей со средним**, и это другая модель
данных (отдельная таблица, а не колонка). Проверить одним вопросом.

### 3. Пункт 10 — это структуры, которые заказчик уже начертил, а мы не подключили

`data/seed/2_Направления_и_ключевые_слова.xlsx` (файл **самого заказчика**) содержит три

## 🔬 Разбор по пунктам

### П.1 — статус «На проверке»

Точное имя — `review`, подпись «На проверке». Списков статусов в коде **четыре**, и они
разошлись:

| Где | Строка |
|---|---|
| `repository.py:24` | `ArticleStatus = Literal["new","review","digest","archive","noise","duplicate"]` |
| `types.ts:535` | те же шесть |
| `ArticlesPage.tsx:27` | те же шесть, свой массив |
| `StatisticsPage.tsx:14` | **пять** — без `new`, свой массив |
| `web/app.html:217` | **четыре** — легаси-фоллбэк |
| `schema.sql:109` (`article_cards`) | семь — есть лишний `rejected` |

**CHECK-ограничений в схеме нет ни одного** (`grep CHECK schema.sql` → пусто). Значит
удаление `review` из кода **не удаляет его из данных**, и расхождение будет тихим.

**Ловушка, которую нельзя пропустить:** `review` — единственный статус, который ставит
система, а не человек — при снятии статьи из дайджеста:
- бэк: `api.py:729` — `target_status = "digest" if patch.selected_for_digest else "review"`
- фронт: `DigestPage.tsx:180` — `updateArticle(articleId, { status: "review" })`

Убрать из выпадающего списка, не назвав замену, — значит сломать «убрать из дайджеста».

Последствия непереведённых строк: счётчик пропадёт из `/api/stats` (проекция по
`ARTICLE_STATUS_VALUES`, `repository.py:2904`), а `<select value={article.status}>`
(`ArticlesPage.tsx:665`) отрисуется пустым.

> **Контекст, о котором стоит помнить:** 22.08 в чате Михаил сам просил Виктора
> «ставь всему статус проверить, чтобы я системно отловить все». `review` был каналом
> «я нашёл косяк». Убирая его, канал надо чем-то заменить — и это ровно пункт 3.

### П.2 — агент обработчик обратной связи

Ветка Германа **смержена** (`fe9f2bd`, PR #62): 10 модулей, 4969 строк + ~4000 строк тестов,
11 новых таблиц. Это агент **по источникам** — подтверждено: все промпты, таблицы и память
про домены, темы и кандидатов-источников. Ни одного места, где агент решал бы про
отдельную статью в ленте.

Честный ответ Виктору на «он на этом обучился?» — **точнее, чем «нет»**:

- на уровне **статьи** — не обучился ничему: пометки не попадают ни в промпт гейта, ни в
  стоп-слова тегов, ни в скоринг, ни в отбор;
- на уровне **источника** — влияют: `compute_source_quality_rows` (`repository.py:1393-1403`)
  считает `noise_count`/`duplicate_count`, формула качества (`repository.py:1549-1563`)
  вычитает `duplicate_rate*10 + noise_rate*5`. Дальше это подсказка человеку в планировщике
  агента, а он **по умолчанию выключен** (`SOURCE_DISCOVERY_ENABLED=0`, `docker-scheduler.sh:52`).

Формулировка для Виктора: **«твои пометки сегодня влияют на оценку источника целиком, но не
на то, как ИИ судит следующую статью».**

**Главное препятствие:** `signal_feedback_events` (`schema.sql:339-351`) — схема полная, три
индекса, нужные типы событий (`marked_noise`, `marked_duplicate`, `comment_added`,
`score_changed`) уже перечислены в `repository.py:250-258`. Но:
- пишет её **единственная CLI-команда** `signal-feedback` (`cli.py:1534`), которую никто не зовёт;
- читает её **никто** — ноль `SELECT` во всём дереве;
- боевой путь пометки `PATCH /api/articles/{id}` → `set_user_article_status` (`api.py:734`)
  в неё **не пишет**.

Значит на проде истории обратной связи почти наверняка **нет**, и «за субботу обучим на
накопленном» — неправда. Начинать надо с записи событий + бэкфилла текущего среза.

**«Создание правил» уже существует — для источников, с кнопкой.** `SourceAgentPage.tsx:767`
создаёт запись `agent_memory` типа `domain`/`topic`, и она реально меняет поведение: домен
со статусом `rejected` выкидывается из поиска (`agent.py:1145` → `:99`). При этом слот
`memory_type='rule'` — **фасад**: API принимает (`api.py:957`), фронт подписывает «Правило»
(`SourceAgentPage.tsx:90`), читателей **ноль**.

Разговор с Виктором надо вести не «построим создание правил», а «такой механизм есть для
источников, нужен такой же для статей».

**Самое дешёвое правило не требует ни строчки кода:** стоп-слова родительских тегов.
Хранение `tags.negative_keywords_json` (`schema.sql:176`), редактирование — готовое поле в
UI (`TagsPage.tsx:164`), применение — **7 точек уже подключены**, включая внешний воркер
(`pipeline.py:94/143/260`, `external_ai.py:127/229/339`, `sandbox.py:272`). Цена — ввод данных.

**Архитектурное ограничение, задающее форму любого решения:** ИИ на проде считается на
внешнем воркере **без доступа к БД**. Всё, что нужно промпту, сериализуется в payload на
РФ-стороне — теги едут именно так, в трёх билдерах (`external_ai.py:40/73/312`) и читаются в
трёх обработчиках (`:99/:201/:319`). **Любой новый блок правил обязан проехать тем же путём,
иначе он будет работать локально и молча не работать на проде.**

Версионирования промптов нет вообще (`grep prompt_version` → 0). Ответить «стало ли лучше
после правки гейта» по данным будет нечем.

### П.3 — рейтинг и комментарии от админа

**Комментарий уже наполовину есть, но он write-only.** Колонка
`user_article_states.analyst_comment` (`schema.sql:262`) заполняется через
`PATCH /api/articles` (`api.py:93` → `repository.py:1739-1754`), но **не читается нигде**:
её нет ни в `SELECT` ленты, ни в `_article_payload` (`api.py:2171-2198`), ни в типе `Article`,
ни в одном компоненте. Это удешевляет половину пункта примерно вдвое — достраиваем мёртвую
ветку, а не пишем с нуля.

**Рейтинга человека нет нигде.** Слово «рейтинг» во фронте — это `Article.rating`, который
приходит из `score_label` AI-скоринга.

**Главная развилка — не UI, а модель данных.** Сейчас статусы и комментарии **строго
пер-юзерные**: `PRIMARY KEY (user_id, article_id)`, админ **не видит** чужие пометки в ленте.
Если рейтинг админа должен быть виден всем — это первое пер-юзерное поле, становящееся
глобальным, и в `user_article_states` оно не ложится: `LEFT JOIN` по `user_id` его у других
просто не увидит. Выбрать «глобально» молча — сломать инвариант, на котором стоит аудит
приватности 24.07.

А если Виктор имел в виду экран-прототип (см. выше) — то нужна не колонка, а **таблица
оценок** (`user_id × article_id × rating`) со средним и счётчиком.

Вторая развилка: влияет ли человеческий рейтинг на сортировку ленты (`score_desc` по
`sc.total_score`, `api.py:622`) и на порог дайджеста (`min_score=60`, `repository.py:4001`).
Смешивание двух шкал уже один раз стоило проекту просадки — keyword-блендинг 0.35/0.65.

### П.4 — «неполный текст, убрать плашку»

Плашка — ровно **один** `<span>`: `ArticlesPage.tsx:652`, текст «неполный текст» встречается
во фронте один раз. Убрать — минуты, падающих тестов нет.

Но за одной формулировкой прячутся **три разные задачи**:

| Вариант | Что делаем | Цена | Что чинится |
|---|---|---|---|
| **а** | удалить бейдж | минуты | ничего — обрывки остаются в ленте, в ИИ и в дайджесте, просто перестают быть отличимыми |
| **б** | не показывать обрывки в ленте | часы (SQL ленты + тумблер + `digest_candidates`) | лента чистая, но расход ИИ не падает — стадии ходят своими выборками мимо ленты |
| **в** | не гнать ИИ по обрывку + переобработка после дозагрузки | **больше дня** | корень: балл 79,6 у статьи в 68 знаков |

**Корень — вариант «в», и он в код не заложен:** `text_truncated` вне `ingestion/`
встречается ровно в 5 местах (`api.py:637/2195` — отдать на фронт, `pipeline.py:247/251/255` —
шаг дозагрузки). Ни одна выборка ИИ-стадий
(`get_articles_needing_summary/tags/scores`, `repository.py:3293/3407/3427`) и ни выборка
дайджеста это поле не упоминают. Слова `reprocess` в коде нет вовсе — 0 вхождений.

**Дозагрузка: ровно одна попытка навсегда.** Очередь берёт `full_text_status IS NULL`
(`repository.py:2719-2754`); после любой попытки статус проставлен — статья выпадает
навсегда. `failed` и `mismatch` не повторяются ничем и никогда. Счётчика попыток в схеме нет.
Ручного повтора нет: `refresh_full_text` (`manual_import.py:183`) зовётся только из ручного
импорта — ни эндпоинта, ни CLI, ни кнопки.

**Флаг и длина разошлись:** `text_truncated` ставится по порогу **280** (`normalize.py:196`),
очередь считает коротким **< 500** (`config.py:43`), планировщик передаёт **800**
(`docker-scheduler.sh:36`). Статья в 400 знаков плашки не имеет, но в очередь идёт. Обратно:
при неудачной дозагрузке флаг ставится в TRUE принудительно (`article_fetcher.py:106,118`),

Побочно: комментарий схемы врёт — `schema.sql:73` перечисляет `blocked` и `paywall`, которых

### П.6 — эмодзи

Фильтрации эмодзи в проекте **нет ни одной строки** (грep по `emoji|surrogate|\U0001F|
unicodedata|смайл` — пусто).

**Замер, который переворачивает «очевидную» реализацию.** На 670 тыс. знаков реальных данных
репозитория (`scripts/digest-2026-08/data`) наивная регулярка на `\p{Extended_Pictographic}`
/ `\p{Emoji}` сработала **11 раз, и все 11 — ложные**: `©`, `®`, `™`, `→`, `↓`, `✓`.
Настоящих эмодзи — ноль. То есть «очевидный» вариант принёс бы только вред.

Работает свойство **`Emoji_Presentation`** (эмодзи-начертание по умолчанию): 0 ложных на тех
же данных, при этом ловит всю telegram-грязь (ZWJ-семьи, тон кожи, флаги, VS16, клавиши).
Граница: режем эмодзи-по-умолчанию + текстовый символ с `U+FE0F` + модификаторы тона + ZWJ +
клавиши; **оставляем** `© ® ™`, валюты, стрелки `→ ↓` (несут смысл: «добыча ↓ 3%»), `± °`, типографику.

**Откуда берутся:** telegram — 15 источников из 120. Заголовок telegram-поста **лепится из
первого предложения тела** (`telegram_parser.py:189` → `_title_from_text`), то есть «🔥» в
начале поста становится первыми символами `articles.title`. А сборка дайджеста берёт
`row.get("title")` — **оригинальный** заголовок (`digest.py:291`), не `title_ru`. **Эмодзи едут
прямо в выпуск заказчику.** Это объясняет, откуда пункт вообще взялся.

**Чинить надо на общем шве** — `repository.insert_article` (`repository.py:2631`), через неё
идут все шесть парсеров. Вход — 2 правки; выход — `digest.py:291` + 6 точек рендера в React.

**Развилка с ценой в дедупе:** `compute_content_hash` (`normalize.py:102`) хэширует
`_normalize_title`, который делает только lower+пробелы. Одна новость из telegram («🔥 Роснефть
запустила…») и с сайта («Роснефть запустила…») дают **разные** хэши и не склеиваются.
Чистить title **до** хэша — дубли начнут ловиться, но разовый проход **обязан** пересчитать
`content_hash`, иначе в базе окажутся два несовместимых поколения ключей.

Ловушка для бэкфилла: **`UPDATE articles SET title` в коде не существует** — заголовок статьи
за всю жизнь системы ни разу не менялся после вставки. Прецедент `repair-terminology`
(`cli.py:281`) трогает только `article_cards`. Это не копипаста, а новая функция записи.

### П.7 — удалить источник

**Удаления нет нигде** — ни в API, ни на фронте, ни в CLI, ни в репозитории. `DELETE`-роутов
в `api.py` четыре (users, tags, scoring-criteria, documents), для sources — ни одного.

**FK защищает, а не убивает:** `articles.source_id REFERENCES sources(id)` **без ON DELETE**
(`schema.sql:65`) → NO ACTION. Наивный DELETE источника со статьями не снесёт их тихо — он
**просто откажет**. Опасность не «потеряем данные», а «сделаем кнопку, которая не работает на
90% источников».

Каскадом уйдут `source_quality_snapshots` (ON DELETE CASCADE, `schema.sql:355`);
`source_candidates.approved_source_id` → SET NULL.

**Три разных смысла слова «удалить», и Виктор сказал одно слово:**
- (а) убрать строку из каталога;
- (б) прекратить сбор — **это уже есть**, `enabled=false`;
- (в) убрать статьи этого источника из ленты — **не делает ни одна операция**: лента джойнит
  sources **без** условия на `enabled` (`api.py:645`). Выключил источник — новое не приходит,
  старый мусор продолжает висеть у всех.

Скорее всего Виктору не хватает именно (в), а называет он это (а).

Отдельно: повторное добавление источника с тем же именем **молча включает выключенный** —
`ON CONFLICT (name, source_type) DO UPDATE SET ... enabled = TRUE` (`repository.py:142-145`).

**Безопасный вариант на сегодня:** разрешить DELETE только при 0 статей (число уже на фронте,
`SourceCard.tsx:41`), иначе кнопка предлагает «Выключить» и объясняет почему. Это закрывает
реальный кейс — источники-призраки от ручного импорта — и не создаёт кнопки массового сноса.

### П.10 — теги и поиск

Полнотекстового поиска **нет**. Единственная точка — `GET /api/articles?search=`, это
`LIKE` по склейке `LOWER(a.title || raw_text || summary)` (`api.py:571-574`). Индексов под
поиск нет ни одного (`CREATE EXTENSION` в проекте не встречается) → seq scan по `raw_text`.

**Теги в поиск не входят.** Набрать «Бурение» в поиске и получить статьи с тегом «Бурение»
нельзя. При этом **поиск в сборщике дайджеста теги уже ищет** (`repository.py:4025-4026`:
`t.name ILIKE` + `parent.name ILIKE`). Два разных поиска в двух файлах.

**Плюс поиск не находит то, что пользователь видит:** ищет по `a.title`, а на экране
`COALESCE(c.title_ru, a.title)` — переведённый заголовок поиском не находится.

Структур сейчас **четыре**, и ни одна не общая: справочник `tags`; склеенная строка
«Родитель / Дочерний» в API (`api.py:2172-2174` — публичный контракт, на нём держатся фронт,
HTML, DOCX и тесты); список тегов в фильтре ленты, который строится **не из справочника**, а
из уже загруженных статей; и две неподключённые структуры из файла заказчика.

**Редактор тегов в UI есть** (родитель, подтег, вкл/выкл, удалить, описание, стоп-слова), но
**нет редактирования ключевых слов** (`keywords_json`/`keywords_en_json`) — хотя именно они
работают и в промпте, и в keyword-фоллбэке. `TagIn` их уже принимает (`api.py:225-227`).

⚠️ **Импортировать 255 поднаправлений «как есть» нельзя.** В промпт тегирования уходит по
строке на тег (`pipeline.py:410-416`); 18 строк превратятся в 273 и подорожает **каждый**
вызов тегирования. Правильный ход — 3–6 курированных подтегов на направление.

включая три самых шумных (Neftegaz.ru, Интерфакс ТЭК, EnergyLand — 72% пометок «шум»). Проверять

**Диагностический слой уже готов и read-only.** Команды (точные имена из `build_parser`):

**Самое полезное и неочевидное:** `POST /api/sources/{id}/diagnose` принимает патч и

Селекторы для молчащих источников можно подбирать **прямо из UI, без записи в БД и без деплоя**.

⚠️ `listing_selector`, не нашедший узлов, **не падает**, а откатывается на всю страницу
(`request_parser.py:240-248`) — источник выглядит починенным и тащит сайдбар.

⚠️ `source-audit` делает живые пробы в 8 потоков боевым UA и может **сам собрать 403/cooldown

### П.12 — почему не идут технологические новости

### П.8/11 — гео-роутинг: механизм есть, выключен

# Хендоф 11.09.2026 — применяются ли новые параметры скоринга

Вопрос владельца: критерии скоринга поменяли в UI — применились ли и когда пойдёт
новый парсинг с новым скорингом. Время везде UTC (MSK = +3).

## Ответ коротко

Применились и уже отработали. Отдельной задачи «на дату» не существует: планировщик
крутит цикл, на проде — раз в 30 минут.

## Что установлено данными

| Факт | Источник |
|---|---|
| Критерии правились 05:51:47, активных 5, сумма весов 100 | `scoring_criteria.updated_at` на проде |
| Задача 3144 `process_articles` → external-ai: 05:54:09 → 05:55:13, status ok | `background_jobs` |
| После правки — 2 скоринговых прогона, последний 05:55:13 | `ai_processing_runs` stage=scoring |
| Свежие баллы посчитаны ровно по 5 новым критериям (1, 789, 791, 792, 793) | `article_score_items` join `scoring_criteria` |
| Статей, ждущих скоринга, — 0 | запрос-копия `get_articles_needing_scores` |
| Цикл: parse 05:43:58 → 05:54:05, затем «Sleeping 1800s» | логи `scheduler` |

Кэша критериев нет ни на одном участке: локальный путь читает их из БД на старте
стадии (`pipeline.py`), внешний воркер получает снимок в момент claim
(`api.py` → `external_ai.build_process_articles_payload`). Даже задача, уже стоящая
в очереди, уедет с новым профилем.

## Что из этого следует (и чего владелец не просил, но это важно)

`ждут скоринга = 0` означает: **весь накопленный корпус оценён по старому профилю**,
где три критерия теперь отключены. Лента и отбор в дайджест ранжируют по этим старым
`total_score`. Новый профиль увидит только то, что принесут следующие циклы парсинга.

Массового перепрогона скоринга в системе **нет**, и обходного пути тоже:

- `score` берёт только статьи с `sc.id IS NULL` — уже оценённые не трогает;
- снести `article_scores` и ждать цикла не поможет: цикл ставит `enqueue-process`,
  чей payload собирается из `get_articles_needing_summary`, т.е. по статьям **без
  сути**, — статьи с готовой сутью туда не попадут;
- `rescore-recompute` не подходит принципиально: у старых статей нет строк
  `article_score_items` под новые `criterion_id`, сумма весов не сойдётся и баллы
  просядут. Плюс его SQL джойнит `scoring_criteria` без фильтра `enabled` —
  отключённый критерий продолжит вносить вклад в total.

Вывод: нужна доработка — задача вида `enqueue-score` (батчи уже оценённых статей
через внешний воркер, `replace_article_score` перезапишет upsert'ом). До неё смена
критериев меняет будущее, но не прошлое.

## Латентный дефект UI (не чинил, только зафиксировал)

Кнопка «Удалить» у критерия уходит в БД немедленно (`DELETE` → `enabled=FALSE`) и,
в отличие от «Сохранить», сумму весов не проверяет. Если уйти со страницы, не добив
веса до 100, следующая стадия скоринга падает целиком, ещё до первой статьи:
`ValueError: Сумма весов критериев должна быть 100, сейчас 70.0` (воспроизведено
локально на `_validate_weights`). 11.09 обошлось — сумма активных равна 100.

## Ложные ходы этой сессии

1. Сначала читал код на ветке `feat/upload-docs` — она отстаёт от `origin/main` на
   16 коммитов (мерж #62, агент источников). Перепроверил все факты на `origin/main`:
   по скорингу расхождений нет, но проверка была обязательной, а не лишней.
2. Ожидал дефолтные 6 часов из compose — на проде оказалось 30 минут. Конфиг в репо
   не равен конфигу прода.
3. Дважды спотыкался на кавычках в SQL через SSH: `$$scoring$$` оболочка подставила
   как PID, `\047` не раскрылось внутри переменной. Рабочий приём — SQL через stdin
   heredoc в `docker compose exec -T db psql`.
4. Канал до прода снова резался VPN (`utun10`), причём флапал: то первая попытка,
   то не поднимался за 8. Лечится циклом ретраев и сбором всех данных одним запросом.

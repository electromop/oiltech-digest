# ADR 0002. Два профиля скоринга: «Бизнес-сигналы» и «Технологический радар»

Статус: принято владельцем 29.09.2026 для фазы 1: профили в данных, вкладки экрана «Скоринг», происхождение балла,
пересчёт по профилю, набор заказчика для профиля business. Профиль «Технологический радар» подключён к оценке радара
30.09-01.10 вариантом Б3 (ветка качества радара по замечаниям эксперта заказчика), раздел «Профиль Б и радар». Для
сигналов после «Отбора» баллы с 25.10 ставит второй вызов «Карточки». Что изменилось после: раздел «Состояние на
ноябрь 2026»; текст о балле статьи ленты и судье радара ниже сохранён как история решения.

## Требование

- Требование заказчика (19.09). Скоринг: два набора параметров, переключение вкладками, без лишнего на экране;
  блоки друг под другом во всю ширину.
  - А. Бизнес-сигналы: стратегическая значимость для нефтесервиса 30; потенциальный бизнес-эффект 25; рыночная
    возможность или изменение рынка 20; практическая применимость 15; достоверность и актуальность 10.
  - Б. Технологический радар: ценность для нефтесервиса 30; технологическая новизна 25; зрелость и
    доказательность 20; переносимость 15; свежесть 10.
  - Карточку радара оценивать так же, как бизнес-сигналы.
- Решение 21.09. Наборы параметров у бизнес- и технологических сигналов разные, теги общие.
- Решение владельца 29.09. Профиль business на проде переводится на набор А явной командой; баллы месяца
  пересчитываются с ИИ только после сухого прогона со стоимостью и его «да».

## Контекст (код до решения)

- Набор критериев один и плоский (`scoring_criteria`), имя уникально глобально, активные отмечены `enabled`.
  Экран «Скоринг» правил его целиком.
- Итог считает код: модель ставит балл по каждому критерию, `final = max(ai, 0,2·kw + 0,8·ai)`,
  `total = Σ final·вес/100` с обрезкой до 100, метки 80/65/40.
- Сумму весов (= 100) проверяли только местные пути. Боевой путь через NL проверял лишь, что список не пуст: при
  сумме не 100 баллы ленты молча искажались.
- Балл не помнил, чем посчитан. Подпункты ссылаются на критерий по id; ни вес, ни текст критерия на момент оценки
  не хранились. API отдавал старым подпунктам текущий вес.
- Записи шли по всей таблице: «Сохранить» выключало всё, чего нет в списке; «Удалить» проверяло сумму всех
  активных; сид по имени добавлял недостающее в bootstrap; пересчёт без ИИ брал все активные критерии без сверки.
- Радар оценивал карточку своим судьёй: один общий балл 0-100 и `interest_score` ревью пачки. Разбивки по
  критериям нет. Выпуск мерил статьи и сигналы одним порогом.
- На проде у business свой набор из пяти критериев с суммой 100, не набор А.

## Решение

1. Профиль: данные. `scoring_criteria.profile ∈ {business, tech_radar}`, имя уникально в пределах профиля.
   Константы и снимок: `oiltech_digest/scoring_profiles.py`.
2. Статья ленты всегда оценивается профилем business. Лента: это бизнес-сигналы, выбора профиля по статье нет.
   Умолчание профиля у выборки критериев, API и команд: business, поэтому прежние пути видят набор ленты без правок.
   **Для сигналов после «Отбора» заменено (#132, 25.10.2026):** баллы сигнала ставит второй вызов «Карточки» по
   профилю его категории: бизнес оценивается набором business, технология набором tech_radar, «другое» не
   оценивается (`signal_scores.py`, `db/signal_scores_store.py`). Итог по весам, ступень и «Решение платформы»
   считает код (`signal_scoring.py`, `repository.platform_decision_sql`).
3. Сумма весов проверяется на всех путях. Ядро не выдаёт задачу с баллами при сумме не 100 (`InvalidJobPayload`
   при сборке пакета), а воркер балла статьи отказывал до первого вызова модели. Сейчас проверка стоит в пакете
   второго вызова «Карточки» (`signal_scores.build_payload`); весов воркер не получает вовсе.
4. Все записи в пределах профиля.
   - «Сохранить» выключает лишнее только в своём профиле; критерий другого профиля по id не правится. Повтор имени:
     400 с объяснением.
   - «Удалить» проверяет сумму профиля удаляемого критерия.
   - Сид заводит набор по умолчанию только в **пустой** профиль (ни одной строки, включённой или выключенной), одной
     транзакцией под своим advisory-lock. Непустой профиль сид не трогает: у business на проде свой набор, и добавка
     сделала бы сумму 200.
5. Набор профиля меняется явной командой `apply-scoring-preset --profile … --preset …`. По умолчанию сухой
   прогон «до и после»; с `--apply` одной транзакцией: прежние активные выключаются (не удаляются: на них ссылаются
   подпункты старых баллов), совпавшие по имени включаются, недостающие заводятся; перед коммитом активны ровно
   критерии набора, сумма 100. Набор `customer`: наборы заказчика А и Б; им же сид заполняет пустой профиль.
6. Происхождение балла. Балл хранит профиль и снимок критериев: id, имя, вес и хэш текста каждого критерия на
   момент оценки. Хэш берёт имя, описание, ключевые слова RU и EN; вес в него не входит.
   - У балла статьи (история) это `article_scores.profile` и `article_scores.criteria_snapshot`; NULL читается как
     business. Разбивка статьи в API берёт вес из снимка.
   - У второго вызова «Карточки» снимок (`signals.criteria_snapshot`) строит ядро при записи. Чтобы баллы писались по
     тем критериям, что видела модель, в задаче едет отпечаток критериев так, как их видит модель
     (`criteria_fingerprints`: имена, описания критериев без линейки, линейки), воркер возвращает его как есть, и ядро
     сверяет его с нынешним. Поменялось то, что видит модель (имя, состав набора, описание критерия без линейки):
     баллы не пишутся, их ставит следующая задача. Правка весов, ключевых слов и описания критерия с линейкой запись
     не держит: модель их не видит, итог, ключевой балл и снимок берут нынешние значения.
7. Пересчёт по профилю и только там, где он верен. Без ИИ, если снимок балла совпадает с текущим набором по id и
   хэшам текстов (отличаются только веса): итог с новыми весами. С ИИ: только после сухого прогона с числом и
   стоимостью и по «да» владельца. Пересчёт без ИИ при правке весов верен, только если вес не входит во вход модели:
   поэтому вес во вход модели не идёт.
8. NL. Форма пакета и итога только расширяется: у критерия поле `profile`, у балла `profile` и снимок. Номер
   контракта тогда остался 1 (`contract.py`). Правка критериев на экране пересборки NL не требует.
9. Экран «Скоринг». Вкладки «Бизнес-сигналы» и «Технологический радар» (`role="tablist"`) отдельной строкой над
   «Нормализовать» и «Сохранить». У вкладки свой список (`?profile=…`), своя сумма весов и своё «Сохранить». Уход с
   вкладки с несохранёнными правками только после подтверждения, правки отбрасываются. На вкладке радара плашка
   объясняет, что оценивается этим набором. API без параметра отдаёт business: старый бандл работает как раньше.

### Профиль Б и радар

- Б1. Профиль Б хранится и правится; судью и выдачу радара не трогаем.
- Б2. Наша функция оценки применяется к принятой судьёй карточке отдельным шагом на NL, итог в новую таблицу.
  Судья остаётся фильтром. Цена: ещё один вызов модели на карточку.
- Б3. Судья сам возвращает баллы по критериям Б из снимка: вызов один, но меняются промпт и схема судьи.

**Выбрано Б3 (30.09).** Вызов модели на карточку один, как и было: судья в том же ответе ставит категорию, дату
события и баллы по критериям; второй вызов Б2 удвоил бы расход ради того же. Критерии tech_radar ядро клало в снимок
задачи (у NL базы нет); при сумме не 100 судья ставил прежний общий балл, и правка весов на экране не роняла прогон.
Вес во вход модели не шёл. Итог хранился на карточке: `signals.score`, `score_profile`, `score_items_json`,
`criteria_snapshot`. Замер 01.10: видимые карточки 55-72, 80 и выше нет, шкала сжата; описания критериев черновые.

**Отход от Б3 для сигналов после «Отбора» (#132, 25.10.2026).** Брать или нет, решает «Отбор», судьи в этой цепочке
нет, и баллы по критериям ставит отдельный второй вызов «Карточки». Он идёт после основного и берёт его поля: стадию
зрелости и дату события из текста. Это ближе к Б2 (свой вызов на карточку, расход под своим именем `signal_scores`),
но итог хранится в колонках `signals`, без отдельной таблицы. Профиль по категории сигнала, а не всегда tech_radar.
Вес во вход модели не идёт. «Свежесть» считает код по дате события из текста, «Зрелость» держится в ступени стадии
карточки (числа в линейках `scoring_rubrics.json`).

## Схема и выкат (29.09)

Схема менялась только добавлениями: колонка `profile` с умолчанием business (прежние строки без UPDATE), CHECK на
профиль, уникальный индекс `(profile, name)`, колонки `profile` и `criteria_snapshot` у `article_scores`. Глобальный
индекс имён снимался вторым шагом, после выката кода: старый код писал `ON CONFLICT (name)`. Итог в `schema.sql`:
чистая база и `init-db` глобальный индекс не вернут.

Порядок выката был такой: SQL до кода (в окно без ИИ-аренд), ядро с `--no-schema`, SQL после кода и `seed-scoring`
(заводит пустой профиль Б, business не трогает), пересборка NL, `apply-scoring-preset` сухим прогоном и с `--apply`,
пересчёт месяца с ИИ сухим прогоном и по «да» владельца. Нельзя было завести строки профиля Б раньше кода, знающего
профили: старый код отдал бы в пакет NL оба набора (сумма 200), и баллы ленты молча раздулись бы.

## Последствия

- (+) Заказчик видит и правит оба набора; лента после выката считалась прежним набором, пока владелец явно не
  поставил набор А.
- (+) «Каким профилем и какими весами посчитан балл» решается по данным, решение о пересчёте вычислимо: без ИИ, с ИИ
  или никак.
- (+) Сумма весов не 100: внятная ошибка задачи, а не тихое искажение баллов.
- (+) Код радара и агента источников, который вёл другой разработчик, не менялся, кроме проверки суммы весов в общем
  `external_ai.py`.
- (−) До подключения профиль Б ни на что не влиял: отсюда плашка на вкладке.
- (−) Выпуск меряет статьи и сигналы одним порогом на двух шкалах: какой балл идёт в выпуск и нужен ли свой порог у
  профиля, решать отдельно.
- (−) Смена набора business сдвигала корпусные доказательства радара: их отбирали по баллу статьи не ниже 40.
- (−) Двухшаговая миграция индекса: порядок выката обязателен.

## Отвергнуто

- Таблица `scoring_profiles` с внешним ключом. Нужна, если у профиля появятся свои данные, которые правят люди
  (порог выпуска, вступление для модели). Сегодня их нет; переход: одна миграция.
- Отдельные таблицы и эндпоинты на профиль. Дублируют сохранение, проверку и экран.
- Веса в коде или конфиге. Заказчик правит критерии на экране.
- Считать статьям оба профиля. Двойная цена, об этом не просили.
- Выбирать профиль статьи по тегу. Теги общие для обоих профилей.
- Менять набор business сидом. Сид запускается сам в bootstrap и не должен менять решения человека; смена набора
  только явной командой после сухого прогона.
- Сдвиг номера контракта. Изменения совместимы, старая сторона пропускает новые поля.

## Открытые вопросы

- Владелец: один порог выпуска на обе шкалы или свой у профиля.
- Заказчик: описания для модели и ключевые слова критериев А и Б (в наборе черновики). Для сигналов после
  «Отбора» решено в #132: «Свежесть» считает код по дате события из текста, «Достоверность и актуальность» модель
  оценивает по линейке, где возраст не учитывается.
- Вопросы к разработчику радара закрыты: подключение Б решено вариантом Б3 (30.09), а с 08.11 судьи и корпусных
  доказательств нет.

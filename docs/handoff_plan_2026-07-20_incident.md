## Сигнатура отказа — запомнить, она обманчива

TCP-рукопожатие проходит, дальше вечная тишина на 22/80/443. `connect()` возвращает успех, потому что успех — это всего лишь приход SYN/ACK; он **не доказывает**, что сервер получил ответный ACK.

Терялись **только пакеты с полезной нагрузкой** в направлении сервер→клиент, на 100%. Служебные проходили. **Размер ни при чём**: пропадал SSH-баннер в 43 байта, при этом ICMP 1400 байт шёл без потерь.

## Ложные версии (4 подряд, каждая выглядела убедительно)

| SYN-прокси / скруббер Timeweb перед ВМ | Закрытые порты (12345/54321/8000/5432) отдают **RST** → отвечает реальное ядро ВМ |

## Метод, который сработал (переиспользовать)

- **Проба заведомо закрытого порта.** RST = отвечает настоящее ядро; «открыт» = отвечает посредник. Разводит «сервер сломан» и «сеть перехватывает» одним замером.
- **`tcpdump -ni any host <IP>` на сервере при непрерывных пробах с клиента.** Показал `Out [P.] length 43` (баннер) + повторы + клиентский `[F.] ack 0` — «отправлено, не доставлено». Это и был приговор.
- **Контроль метода обязателен.** `nc` для баннера врёт (github.com:22 тоже дал «пусто» из-за буферизации) — переписал на python-сокет. Без контрольной пробы вывод был бы ложным.
- **Проверять собственный вантаж.** Три «независимые» точки (Mac, фетчер Anthropic, 2 веб-прокси) оказались все зарубежными. Китайский и индийский сканеры в трассе сервер обслуживал нормально — это и вскрыло, что дело в маршруте.

## Ошибки разбора, которые стоит помнить

- **Фетчер Anthropic назван «независимым подтверждением пакетной сигнатуры» — неверно.** Это HTTP-клиент: не умеет сырой TCP, не видит SSH-баннер. Он доказал только «HTTPS не отвечает», что одинаково объясняется и «сервер лежит». Пакетная сигнатура снята с ОДНОЙ точки; независимым подтверждением стал лишь `tcpdump` со стороны сервера.
- **Проглядел ранний сигнал:** RTT 150 мс и TTL 58 до Питера с «домашнего» канала РФ при норме 5–40 мс. Это с самого начала указывало на туннель.

## Что дальше — задача «чистка РФ-core»

**Не начата. Блокеры:**

1. **Доступ.** Пока VPN активен, SSH с Mac не пройдёт тем же мёртвым маршрутом. Ключ `id_ed25519` и запись в `known_hosts` на месте. Нужно явное «да» владельца на SSH (правило: никаких действий с сервером без подтверждения).
2. **Судьба чужого контейнера `emo_tracker-tracker-bot-1`.** Не дайджест, ест те же 1.9 ГБ, формально «лишнее» — но это чья-то работа. Не трогать без явного решения владельца.

**План работ (после снятия блокеров):**

1. Read-only опись: контейнеры, образы, тома, куда ушли 18 ГБ.
2. Список с размерами на утверждение владельцу — построчно.
3. Удаление только после подтверждения. Кандидаты по убыванию отдачи: неиспользуемые образы и build-кэш (обычно 3–8 ГБ), ротация логов, осиротевшие тома, старые файлы в `~`.
4. **Тома — в последнюю очередь и только с отдельным подтверждением по каждому**: перепутать том с базой = потерять 10 516 статей.

**Памятка по деплою (не изменилась):** RAM 1.9 ГБ, `docker compose down` перед `up -d --build`, не собирать при живом стеке.

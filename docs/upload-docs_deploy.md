# Выкат приёма файлов на прод — чек-лист

Ветка `feat/upload-docs`. РФ-ядро СПб `109.68.213.12`, внешний воркер Амстердам `85.234.107.233`.

> ⚠️ Ни один шаг здесь мной не выполнен. Нужен явный «да» владельца на доступ к серверу.

## Что должен сделать владелец своими руками

**Переменная модели в `.env` внешнего воркера.** Файл не в git, я его не вижу.
Без неё стадия разбора падает с явной ошибкой — это сделано намеренно: тихий откат
на основную модель уже случался, и корпус разобрала бы самая дешёвая.

```
OPENAI_DOC_MODEL=gpt-5.4-mini
OPENAI_DOC_REASONING=medium
```

⚠️ **Модели `gpt-5.5-mini` не существует** — проверено списком моделей, доступных ключу.
Есть `gpt-5.5` (без mini) и `gpt-5.4-mini` (самый свежий mini). Взят `gpt-5.4-mini`
как «более новый mini, чем был». Переключение на `gpt-5.5` — правка этой одной строки,
но цена вырастет: ставки 5,00/30,00 против 0,75/4,50, то есть примерно в 6,7 раза.

## Порядок выката

Внешний воркер и ядро должны нести ОДИН И ТОТ ЖЕ код: тип задачи `process_document`
знают оба. Ядро гидрирует, воркер исполняет.

1. **Проверить, что нет активных ИИ-задач.** Рестарт рвёт lease внешнего воркера —
   на этом уже горели 24.07, воркер 80 минут жёг деньги в петле.
   ```sql
   SELECT id, kind, status FROM background_jobs WHERE status IN ('running','finalizing');
   ```
2. **Снять дамп базы до выката.** Бэкапов по крону нет (#34), это единственная страховка.
3. **РФ-ядро:** `git fetch && git reset --hard origin/<ветка>` → сборка → `up -d`.
   ⚠️ Сборка на 1,9 ГБ с задокументированным OOM. Собирать по одному сервису,
   а не всё сразу; при нехватке памяти — остановить `playwright-worker` на время сборки.
4. **Схема применится сама** при старте bootstrap: новые таблицы создаются
   `CREATE TABLE IF NOT EXISTS`, изменение таблицы расходов — в идемпотентной секции.
5. **Внешний воркер (Амстердам):** тот же код + переменная модели, затем рестарт.
6. **Дымовая проверка:** зайти админом → «Материалы» → загрузить документ →
   дождаться карточки. Ожидаемое время для файла на 10–15 страниц — до минуты.

## Откат

```
git reset --hard <предыдущий коммит> && пересборка && up -d
```
Том `documents` при откате остаётся — он ничему не мешает, таблицы тоже.
Приём файлов можно погасить без выката кода: `UPLOAD_DOCS_ENABLED=false` и рестарт `app`.

## Замеры, на которых основаны решения

Прогоны на реальных документах владельца, 21.08, модель `gpt-5-mini`:

Три реальных документа владельца, все три формата, модель `gpt-5-mini`:

| Документ | Объём | Фрагментов | Время | Стоимость | Фактов | Подтверждено |
|---|---|---|---|---|---|---|
| Презентация, 13 слайдов | 10 418 знаков | 1 | 43 с | $0,025 | 32 | **32 (100%)** |
| Отчёт НИР, 94 блока | 22 960 знаков | 3 | 58 с | $0,033 | 25 | **24 (96%)** |
| Заключение экспертизы, 107 стр. | 104 431 знак | 10 | 164 с | $0,121 | 226 | **146 (65%)** |

Заключение экспертизы — худший случай намеренно: это государственная экспертиза
с таблицами, растянутыми через страницы, и 67 страниц из 107 в нём вообще без
текстового слоя (наполовину скан). 65% на таком документе — честный результат;
неподтверждённые числа показываются с пометкой и в сравнения не идут.

**Три дефекта вскрыл только живой прогон**, офлайн-заглушка их показать не могла:

1. Весь бюджет ответа съедало РАССУЖДЕНИЕ модели: 2496 reasoning-токенов, 0 выходных.
   Фича падала бы всегда. Лечение: бюджет 8000, усилие рассуждения на извлечении `low`.
2. Сверка отбивала верные факты, потому что не снимала `>`, `≈` и ярлык перед двоеточием.
3. Во фрагментах НЕ БЫЛО пометок номера страницы — модель угадывала, на какой странице
   стоит число, и 30 «неподтверждённых» из 60 находились на другой странице. Промпт
   пометки ожидал; их не давал payload. После правки сверка выросла с 27% до 65-100%.

Плюс: единица измерения нормализуется («метр» = «м», «гектар» = «га»), но подмена
величины (барр ≠ тонн) и масштаба (млн ≠ млрд) остаётся строгим отказом.

## Что НЕ вошло в этот выкат

Сознательно отрезано под срок, каждое — отдельный тикет:

- балл документа, направления, справочник компаний, публикация в общий корпус (#38, #39, #40)
- пакетная загрузка и квоты сверх лимита на файл
- хранилище частичных результатов: падение на позднем фрагменте переоплачивает
  предыдущие. На единичных документах это центы, на корпусе — нет
- разбор файла идёт ИНЛАЙНОМ в веб-процессе, а не в фоновой задаче. Основание —
  замер: pypdf держит пик 35 МБ на 299-страничном документе, а размер файла ограничен
  25 МБ. При переезде на более мощный сервер разбор уезжает в воркер
- закрытие открытой регистрации (#33). Обойдено иначе: **загрузка доступна только
  администратору**, поэтому открытая регистрация права загрузки не даёт
- резервное копирование тома с оригиналами (#34). Загруженный документ сейчас
  невосстановим — это осознанный риск на период демонстрации

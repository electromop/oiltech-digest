# Формат обмена с потребителем выпуска, версия 2

Выпуск месяца платформа отдаёт внешнему сервису (дальше: потребитель) пакетами: выпуск месяца, дозагрузка и
обновление карточек. Пакет подписан ключом платформы и зашифрован на ключ потребителя. Потребитель сам забирает пакеты из
точки обмена платформы, платформа к нему не ходит; туда же он отдаёт квитанции на пакеты и пакеты откликов своих
сотрудников. Это описание общее для обеих сторон: тот же формат у потребителя, общий образец содержимого
лежит в тестах обеих сторон (здесь `tests/exchange_samples/release-2026-09.json`), расхождение ловят тесты. Версию 1
платформа не отправляет.

## Файл пакета

JSON-объект в UTF-8 ровно с такими полями:

| Поле | Значение |
|---|---|
| `format` | строка `digest-exchange-package` |
| `version` | число `2` |
| `signer` | отпечаток ключа подписи платформы |
| `recipient` | отпечаток ключа потребителя, на который зашифрован пакет |
| `ciphertext` | зашифрованное содержимое, base64 |
| `signature` | подпись, base64 |

Отпечаток ключа: первые 8 байт SHA-256 от 32 байт открытого ключа, 16 знаков hex строчными буквами. base64 со
стандартным алфавитом и выравниванием `=` (RFC 4648, раздел 4).

## Как собран

1. Содержимое (следующий раздел) записано в JSON, UTF-8.
2. Зашифровано по HPKE (RFC 9180), режим base: KEM DHKEM(X25519, HKDF-SHA256), KDF HKDF-SHA256, AEAD
   ChaCha20-Poly1305, на открытый ключ потребителя X25519. `info`: байты ASCII `digest-exchange-package/2`, `aad`
   пустой. В `ciphertext` идут enc (32 байта) и сразу за ним шифротекст.
3. Подписано Ed25519 (RFC 8032) ключом платформы: байты ASCII `digest-exchange-package/2`, за ними сразу байты
   `ciphertext` (до base64).

Строка формата входит в подпись и в шифрование: подпись и шифротекст версии 2 не годятся ни для какой другой версии.
Потребитель проверяет подпись до расшифровки. На Python с библиотекой cryptography 50.0.2 (версия закреплена у обеих
сторон):

```python
from cryptography.hazmat.primitives import hpke

suite = hpke.Suite(hpke.KEM.X25519, hpke.KDF.HKDF_SHA256, hpke.AEAD.CHACHA20_POLY1305)
ciphertext = suite.encrypt(content_bytes, consumer_public_key, info=b"digest-exchange-package/2")
signature = platform_signing_key.sign(b"digest-exchange-package/2" + ciphertext)
```

## Содержимое: выпуск и дозагрузка

| Поле | Значение |
|---|---|
| `number` | номер пакета: целое больше 0, у каждого пакета свой |
| `kind` | `release` (выпуск месяца) или `addition` (дозагрузка) |
| `month` | месяц выпуска `ГГГГ-ММ` |
| `cards` | карточки, список; у выпуска может быть пустым, у дозагрузки нет |

Карточка это тексты и атрибуты сигнала так, как их показывает витрина платформы, с правками людей. Баллов, «Решения
платформы» и причины отказа отбора в пакете нет. Все поля обязательны; `null` и пустая строка значат «не заполнялось»;
«не определено» приходит строкой справочника платформы. В одном пакете карточка сигнала один раз.

| Поле | Значение |
|---|---|
| `signal_id` | номер сигнала на платформе, целое больше 0; у дубля номер корня его склейки |
| `title` | заголовок, не пустой |
| `summary` | суть |
| `why_important` | «почему важно»: объект `{"text": ..., "set_by": ...}` или `null` |
| `hypothesis` | «Гипотеза для Компании»: текст или `null` (новое в версии 2) |
| `theme` | тема |
| `event_date` | дата события `ГГГГ-ММ-ДД`; если известны только месяц или год, первый день этого месяца или года; `null`: дату понять нельзя (ни день, ни месяц, ни год), читатель видит «Дата не определена» |
| `event_type` | тип события |
| `companies` | компании-участники: список строк, может быть пустым |
| `region` | регион |
| `technology_class` | класс технологии |
| `maturity` | зрелость технологии |
| `oilfield_relevance` | связь с нефтесервисом словами справочника: прямая, переносимая, нет связи |
| `oilfield_application` | как применяется в нефтесервисе |
| `updated_at` | когда платформа увидела карточку в таком виде: дата и время ISO 8601 с часовым поясом |
| `publications` | публикации в порядке платформы, свои и склеенных дублей: список, может быть пустым |

`set_by` у «почему важно»: `agent` (агент карточки), `human` (человек) или `radar` (судья радара, а также старые
карточки без пометки автора).

Публикация:

| Поле | Значение |
|---|---|
| `title` | заголовок |
| `source` | источник: издание или канал |
| `url` | ссылка `http` или `https`, обязательна |
| `date` | дата публикации `ГГГГ-ММ-ДД` по Москве |

## Содержимое: обновление

Изменения карточек на платформе после того, как они ушли потребителю. Месяца у обновления нет.

| Поле | Значение |
|---|---|
| `number` | номер пакета: номера у всех пакетов для потребителя общие |
| `kind` | `update` |
| `cards` | изменённые карточки в том же виде, что в выпуске; список, может быть пустым |
| `merges` | склейки: список объектов `{"signal_id": ..., "merged_into": ...}`, может быть пустым |
| `removals` | номера сигналов, снятых с платформы: список, может быть пустым |

Сигнал в пакете обновления встречается один раз: карточкой, склеенным или снятым. Оставшийся сигнал склейки
(`merged_into`) в этом же пакете не склеен и не снят, но может прийти карточкой: так приходит сигнал, которого
потребитель ещё не видел. Пустое обновление не выкладывается.

- Карточка: отправленный сигнал, чья карточка на платформе изменилась (правка людей, новая публикация, новый атрибут,
  гипотеза). `updated_at`: когда платформа увидела карточку в новом виде.
- Склейка: отправленный сигнал стал на платформе дублем; `merged_into` корень его склейки. Номер, ушедший склейкой,
  больше не отправляется; расклейку формат не передаёт.
- Снятие: отправленный сигнал не действует по явному решению: в архиве, убран людьми, отклонён отбором, его статья
  помечена на удаление. Правила показа, которые срабатывают сами (срок события, правила качества), смена категории и
  архив источника снятия не дают.
- Возврат: снятый сигнал снова действует; его карточка приходит с `updated_at` новее снятия, уже после квитанции
  потребителя на пакет со снятием.

## Пакет откликов

Отклики сотрудников потребителя на карточки, без участника и группы. Конверт тот же (раздел «Файл пакета»), в обратную
сторону: `signer` это отпечаток ключа подписи потребителя, `recipient` отпечаток ключа платформы для расшифровки
откликов; подпись и шифрование с той же строкой формата.

| Поле | Значение |
|---|---|
| `number` | номер пакета откликов: свой счёт потребителя, целое больше 0 |
| `kind` | `reactions` |
| `source` | метка источника: непустая строка до 200 знаков |
| `reactions` | отклики в порядке нажатия: непустой список |

Отклик:

| Поле | Значение |
|---|---|
| `signal_id` | номер сигнала платформы, который уходил потребителю (у склеенного: и номер дубля, и номер корня) |
| `reaction` | `save`, `work`, `export`, `useful`, `not_oilfield`, `not_new`, `few_facts` или `card_error` |
| `placed` | `true` отклик поставлен, `false` снят |
| `day` | день по Москве `ГГГГ-ММ-ДД` |

Платформа проверяет по порядку: формат и версию файла, подпись открытым ключом потребителя до расшифровки, получателя,
расшифровку своим ключом, содержимое (поля ровно такие, виды из списка, номера сигналов из отправленных). Первое
несовпадение: отказ с причиной, откликов у платформы не прибавляется. Тот же номер с тем же содержимым: «уже было», с
другим содержимым: отказ. Счёт откликов платформа ведёт по корню склейки на момент чтения: «в работе у N групп» это
поставлено минус снято `work`.

## Точка обмена

Адрес точки с версией адресов (не формата): `https://<платформа>/api/exchange/v1`. Каждый запрос несёт заголовок
`Authorization: Bearer <токен>`. Точка пускает только адреса потребителя: чужой адрес получает `403` и до приложения
не доходит; без верного токена `401`. Отказ ставится до чтения тела запроса. Адрес потребителя внешний (публичный):
частный адрес платформа не отличает от адреса своего прокси и не пускает.

| Запрос | Ответ |
|---|---|
| `GET /packages` | `200`, JSON `{"packages": [1, 2, 3]}`: номера всех пакетов для потребителя по возрастанию |
| `GET /packages/{номер}` | `200`, файл пакета (раздел «Файл пакета»); такого пакета нет: `404` |
| `PUT /receipts/{номер}` | квитанция на пакет; `200` записана или уже была; другая на тот же номер `409`, номера нет `404`, не по формату `422` |
| `PUT /reactions/{номер}` | пакет откликов; `200` принят или уже был; номер занят другим содержимым `409`, отказ проверки `422` |

Квитанция: JSON без конверта ровно с полями `number` (номер пакета, тот же, что в адресе), `outcome` (`accepted` принят,
`already` уже был, `rejected` отклонён) и `message` (ответ потребителя на пакет одной строкой). Ответ на пакет
откликов: JSON `{"number": ..., "outcome": "accepted" | "already", "message": ...}`; отказ: `{"detail": "Отклонено:
<причина>."}`. Отказы точки платформа хранит для своего журнала обмена.

Номер пакету даёт база при сборке, сборка и выкладка идут одной транзакцией под одним замком: пакет с большим номером
не появляется раньше пакета с меньшим. Пакеты не удаляются и не меняются: повторный запрос отдаёт тот же файл.
Потребитель забирает номера, которых ещё не брал, по порядку номеров.

## Какие пакеты собирает платформа

- Выпуск месяца: тот же состав, что у выпуска платформы на закрытии месяца (как в PDF и выгрузке): статья идёт
  сигналом своей публикации, дубль корнем склейки. Месяц без отметок даёт пустой выпуск. Выпуск у месяца один. Его
  собирает шаг планировщика в первом цикле после закрытия месяца; месяцы до запуска собирает команда. Если у статьи
  выпуска ещё нет сигнала, выпуск не собирается, пока сигнал не заведут: иначе состав разошёлся бы с платформой.
- Дозагрузка: сигналы по списку номеров с месяцем выпуска. Дубль уходит корнем склейки; номер, которого нет, и сигнал,
  который не действует (в архиве, убран людьми, отклонён отбором, статья помечена на удаление), дают отказ со списком;
  уже отправленный сигнал пропускается.
- Обновление (раздел «Содержимое: обновление»): шаг планировщика раз в сутки по Москве и кнопка в журнале обмена.

## Ключи

Ключи лежат в настройках ядра платформы, вне репозитория: base64 от 32 байт, несколько через запятую. При смене ключа
старый и новый действуют вместе: первый в списке подписывает и шифрует, пакет называет свой ключ отпечатком.

| Настройка ядра | Ключ |
|---|---|
| `EXCHANGE_SIGNING_KEYS` | закрытый ключ подписи платформы, Ed25519; открытую часть получает потребитель |
| `EXCHANGE_DECRYPTION_KEYS` | закрытый ключ платформы для расшифровки откликов, X25519 |
| `EXCHANGE_CONSUMER_KEYS` | открытый ключ потребителя X25519: на него шифруются пакеты |
| `EXCHANGE_CONSUMER_SIGNING_KEYS` | открытый ключ подписи потребителя, Ed25519: им проверяются отклики |

Пару ключей платформы выпускает команда `exchange-new-key --kind signing` (или `decryption`): закрытая часть идёт в
настройку, открытая с отпечатком передаётся потребителю. Адреса потребителя (`EXCHANGE_CONSUMER_IPS`, IP или сеть через
пробел) и SHA-256 его токена (`EXCHANGE_TOKEN_HASH`) тоже в настройках ядра.

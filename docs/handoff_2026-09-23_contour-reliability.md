Решения, которые принял я и которые стоит проверить глазами владельца:

1. **Частичный итог при остановке.** Требование «для уже записанных статей ИИ повторно не вызывается»
   выполнимо только так: воркер отдаёт сделанное (`partial`), ядро пишет его как при `complete` и вычитает
   из задачи (явный список — без обработанных, пакет «N статей» — N уменьшается). Сбор и документ
   частичного итога не отдают — возвращаются целиком (сбор ИИ не зовёт; итог документа — одна карточка).
2. **Замок на всё время жизни планировщика, а не на цикл.** С замком на цикл два экземпляра шли бы
   по очереди — без наложения, но со сбором и постановкой ИИ вдвое чаще, то есть тот же дубль 21.09.
3. **`deploy-core.sh` прогоняет `init-db` (схему) до перезапуска.** Это не bootstrap: без сидов,
   только идемпотентные CREATE/ALTER, которые раньше шли при каждом полном `up`. Без этого новый код
   встретил бы старую схему. Отключается `--no-schema`.
4. **Сроки остановки:** 30 с на завершение + 60 с на шаг + 15 с на отчёт → `stop_grace_period: 120s`.
   Тест сверяет compose с `config.py`.

## Выкат

**РФ (после B):** `cd /root/oiltech-digest && git fetch origin && git reset --hard origin/main &&
scripts/deploy-core.sh app scheduler worker playwright-worker` — дальше скрипт сам: сборка, схема,
страж ИИ-аренд, перезапуск, health, `check-lanes`. Первый раз скрипта на сервере ещё нет — поэтому
fetch/reset руками; дальше хватает `scripts/deploy-core.sh <сервисы>`. После выката ядра до пересборки
NL `check-lanes` честно звенит `contract_mismatch` у всех четырёх воркеров — так и должно быть.

**NL (владелец, веб-консоль Timeweb):** `cd /root/oiltech-digest && git fetch origin &&
git reset --hard origin/main && scripts/deploy-nl.sh`. Контейнеры идут по одному; каждый следующий —
только когда предыдущий отметился в ядре новой сборкой. На первый раз (старые воркеры без SIGTERM)
задачи в работе вернутся по аренде, как раньше; со второго выката — сразу. Старый воркер — `python`
под PID 1 без обработчика SIGTERM, сигнал он игнорирует; скрипт узнаёт его (нет команды
`worker-versions`) и гасит за 10 с, а не ждёт 120 с ради того же SIGKILL.

**Проверки после NL (на РФ):**
- `docker exec oiltech_app python -m oiltech_digest.cli check-lanes` — четыре строки версий, без тревог;
- `docker exec oiltech_pg psql -U oiltech -d oiltech_digest -c "SELECT count(*) FROM background_jobs WHERE status='running' AND execution_region='external' AND lease_expires_at < now()"` → 0;
- `docker logs oiltech_app --since 5m 2>&1 | grep -c 'POST /api/external-worker/claim'` в простое → ≤ ~60;
- если пересборка попала на ИИ-пакет: у задачи `error_message` «Возвращена воркером (…); сделано до остановки: N».

## Ловушки и ложные версии

- **Часы ВМ colima спешат и раз в минуту подводятся назад (~200 мс).** Тест «ядро не выдало задачу»
  падал 2 раза из 25 прогонов: только что созданная задача была «из будущего» (`run_after` > `now()`
  базы). Оба сбоя ровно через 60 с друг от друга. Продукт это не задевает; тесты повторяют `claim` до 2 с.
- **macOS `/bin/sh` (bash 3.2) при `LC_CTYPE=C.UTF-8` считает байт `»` частью имени переменной:**
  `"«$svc»"` → `svc\xc2: unbound variable`. В скриптах — `${svc}`.
- `sitecustomize` импортируется раньше, чем `python -m` добавит каталог в `sys.path`, — для замедлителя
  модели в живом прогоне каталог репозитория нужен в `PYTHONPATH`.
- Шаг планировщика живёт в своей группе процессов: после `kill -9` обёртки он сиротой держит pipe
  stdout открытым, и чтение вывода висит. В тестах вывод — в файл.
- Локально нет плагина `docker compose`; есть `docker-compose` 5.1.4 из Homebrew.

## Детали, которые нельзя забыть

**Бэкапы БД.** В `/root/oiltech-backups` теперь 3 дампа (9, 10, 22 июля). Это **единственные** бэкапы — автоматического крона нет. Снять свежий: `docker exec oiltech_pg pg_dump -U oiltech -d oiltech_digest | gzip > /root/oiltech-backups/oiltech_$(date +%F_%H-%M).sql.gz`. **Стоит завести крон** (открытая задача).

**Ротация логов — host-level, НЕ в репозитории.** Конфиг `/etc/docker/daemon.json`:
```json
{"log-driver":"json-file","log-opts":{"max-size":"10m","max-file":"3"}}
```
Переживает деплой (`git pull` его не трогает), но **не виден в `docker-compose.yml`**. При пересоздании сервера с нуля восстановить вручную. Валидировать `dockerd --validate --config-file=...` ДО `systemctl restart docker` — кривой конфиг не даёт демону подняться.

**Хранилище образов = containerd.** Docker 29.5.3 использует containerd image store → образы и часть кэша лежат в `/var/lib/containerd` (~13 ГБ до чистки), а не в `/var/lib/docker`. `docker system df` — источник правды по reclaimable. Образы 4.5 ГБ активны, dangling нет (containerd дедуплицирует слои 5 oiltech-образов).

**emo_tracker.** `emo_tracker-tracker-bot-1` — личный Telegram-бот electromop (github.com/electromop/emo_tracker), к дайджесту отношения не имеет, был нерабочий (не достучаться до Telegram с РФ-датацентра). Остановлен: `docker update --restart=no` + `docker stop`. Поднять обратно: `docker start emo_tracker-tracker-bot-1`. Исходники в `/root/emo_tracker` целы. Ел всего 13 МБ RAM — не влиял на OOM-риск.

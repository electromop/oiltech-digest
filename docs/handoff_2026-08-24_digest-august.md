# Две правки после импорта на прод (24.08, вечер)

## 1. `too_short` больше не означает два разных исхода

**Как заметили.** При ручном импорте пяти статей четыре вернули `too_short`, причём
у одной при этом было 40 297 знаков. Выглядело как поломка — на деле тексты в базе
целы.

**Что происходило.** `fetch_article_text` возвращал `too_short` в двух несвязанных
случаях: (а) страница действительно куцая, извлекли меньше `min_chars`; (б) извлекли
нормально, но не вдвое больше уже сохранённого (`MIN_GAIN_RATIO = 2.0`) — то есть
текст у статьи ЕСТЬ и он не хуже, перезаписывать нечем. Второе — штатный отказ от
бесполезной перезаписи, а не сбой.

Запись при этом была и остаётся безопасной: при не-`ok` статусе `raw_text=None`, а
`update_article_full_text` в этой ветке правит только статусные поля и **не трогает
сам текст**.

**Что сделано.** Случай (б) выделен в отдельный статус `no_gain`:

- `article_fetcher.fetch_article_text` — разделение по `len(best) >= min_chars`;
- `fetch_full_text` — свой счётчик, CLI печатает «без прироста=N» отдельно от
  «слишком коротких»;
- `repository.get_articles_needing_full_text(retry_too_short=True)` — теперь
  `IN ('too_short','no_gain')`. **Список, а не равенство**: в базе с прежних прогонов
  лежат строки, где «нет прироста» записано как `too_short`, и при равенстве часть
  статей молча выпала бы из повтора;
- обновлены комментарий в `schema.sql`, справка CLI, `docs/testing.md`.

**Миграции нет и не нужно.** Исторические строки остаются с `too_short` — значение
поля информационное, по значениям его нигде не разбирают (в API отдаётся строкой, во
фронте тип `string | null`, ветвлений нет). Новые прогоны будут писать честный статус.

**Тесты:** 3 новых в `tests/test_article_fetcher.py` — `no_gain` при уже сохранённом
теле, `too_short` на реально куцей странице, и страховка «`no_gain` не затирает текст».
Весь набор: **361 зелёный**.

## 2. Неверная команда psql в консоли

В `docs/upload-docs_console.md` в четырёх местах стояло
`docker compose exec -T oiltech_pg` — но `oiltech_pg` это `container_name`, а имя

  строку «реками».
- `digest.py` — `render_digest_pdf` печатает номера страниц (`display_header_footer`,
  константа `_PDF_FOOTER_TEMPLATE`). Chromium рисует колонтитул **только в полях**,
  поэтому нижнее поле стало 12 мм; верхнее осталось нулевым, чтобы hero-баннер
  по-прежнему упирался в край листа. Влияет на все будущие выпуски.

## Побочный дефект, который внесло выравнивание

Justify рвёт строку по пробелу — и «15 000 футов» разъехалось на «15» в конце строки
и «000 футов» в начале следующей. Вылечено **общим** типографским проходом
(`protect_numbers` в `build_digest.py`), а не подстановкой трёх строк: в следующем
выпуске числа будут другие. Правило прогнано на 11 случаях.

Первая версия правила была неверной, и это показал прогон, а не чтение: захватывающая
регулярка съедала цифру, и в «1 234 567» склеивалась только первая пара; а `\b` после
`%` не срабатывает вовсе, поэтому «20 %» оставалось разрывным. Переписано на просмотры
назад/вперёд без захвата.

# JPT: почему недобирал и что починено (25.08)

Просьба заказчика (#428969–428972): «JPT — маст хэв, номер 1 в мире, а оттуда мало
что подтягивается». Диагностика по `/diagnosing-bugs`.

## Петля обратной связи

Прод недоступен (VPN включён), поэтому петля локальная и не ходит в сеть: страница
`jpt.spe.org/latest-news` отрендерена один раз и сохранена, дальше по ней гоняется
**настоящий** `extract_candidate_links` с конфигурацией как на проде. Вердикт
одинаковый от запуска к запуску, отрабатывает за секунду.

## Замер: ДО

```
страница 219 КБ, ссылок на свой домен 92
парсер нашёл кандидатов: 42   (прод берёт первых 6)
  из них рубрики /topic/..., а не статьи: 30
  с датой публикации: 0
первый по оценке кандидат: /topic/fracturing-pressure-pumping — РУБРИКА
```

Заметка от 22.08 говорила «парсер находит всего 5 кандидатов». Это была правда о
**выдаче**, а не о разборе: кандидатов 42, просто прод берёт первых шесть, и первым
идёт рубрика.

## Три независимые причины

1. **Селекторы не заданы.** Якорный эвристический путь тащит всё подряд: 30 рубрик из
   42, причём рубрика выигрывает ранжирование и занимает слот.
2. **Дата не разбирается даже с правильным селектором.** В карточке она лежит вместе с
   автором и изданием: `August 25, 2026 • JPT Staff • Journal of Petroleum Technology`.
   `dateparser.parse` на такой строке возвращает None → `published_at=None` → пустой
   `last_seen_published_at`. **Это и есть причина, по которой источник годами выглядел
   «замолчавшим».**
3. **Канала настройки не существовало.** `apply_overrides` читал и писал только
   `listing_selector`; `article_link_selector` и `article_date_selector` не
   поддерживались вовсе — прописать их в реестре было бы молчаливым no-op.

Сеть и блокировки исключены замером: страница рендерится, 219 КБ, ни WAF, ни challenge.

## Почему НЕ fuzzy-разбор

Очевидное решение — `dateparser.parse(fuzzy=True)`. Прогнал на ловушках: он **выдумывает
даты**. «Section 5 of 12» → 2026-05-12, «Halliburton 2026 Q3 results webcast» →
2026-03-25. Поэтому запасной путь сначала вырезает регуляркой **форму** даты и разбирает
только её: все реальные строки проходят, все четыре ловушки дают None.

## Что изменено

- `request_parser._parse_datetime` — запасной путь через `_DATE_IN_TEXT_RE`. Общий для
  **всех** источников, не только JPT.
- `source_overrides.apply_overrides` — научен `article_link_selector` и
  `article_date_selector` (чтение, сравнение, запись, лог).
- запись JPT в `SOURCE_OVERRIDES` — три селектора по разметке Arc Publishing:
  `.PromoB, .PromoA` / `*-title a` / `*-by-line`. Заодно снят неверный комментарий
  «даты извлекаются».
- 3 регрессионных теста в `tests/test_request_parser.py`, включая тест-ловушку на
  выдуманные даты. Весь набор: **364 зелёных**.

## Замер: ПОСЛЕ

```
парсер нашёл кандидатов: 12
  рубрик: 0
  с датой публикации: 12
```

12 уникальных статей при 14 карточках на странице — две ссылки PromoB совпали с
избранными PromoA и схлопнулись дедупом, потерь нет.

## Осталось решить: `REQUEST_ARTICLE_LIMIT = 6`

Теперь главный ограничитель — не разбор, а **глобальный потолок**: со страницы доступно
12 статей, прод берёт 6. Значение в `config.py` дефолтное (`os.environ.get(...,"6")`),
фактическое на проде не проверял — нужен доступ. Поднимать его — решение владельца:
настройка **общая для всех** request/playwright-источников, а не только для JPT.

## Чтобы починка доехала до прода

Правки не закоммичены. После коммита и пуша:

```bash
ssh root@109.68.213.12 'cd /root/oiltech-digest && git fetch origin && git reset --hard origin/<ветка> && docker compose build app worker scheduler tasks && docker compose run --rm app python -m oiltech_digest.cli apply-source-overrides'
```

## Найдено попутно, не чинил

`_parse_datetime` не понимает русские месяцы: «19 августа 2026» не разбирается ни
строго, ни через новый запасной путь. Это не регрессия — так было всегда, но для
российских источников симптом ровно тот же, что был у JPT: пустой `published_at`.
Отдельная задача.
